# DzenPilot — архитектура приложения

## 1. Общая идея

DzenPilot — веб-сервис для авторов Яндекс Дзена. Он решает четыре задачи:

1. Анализ конкурентов.
2. Поиск прибыльных тем.
3. Создание статей с помощью ИИ.
4. Планирование и подготовка публикаций.

Сервис устроен как классическое трёхзвенное приложение: браузер → API → база данных,
плюс отдельная очередь фоновых задач для долгих операций (анализ конкурентов, генерация
статей, плановые публикации).

## 3. Слои backend

| Слой | Каталог | Ответственность |
|------|---------|-----------------|
| API | `app/api/v1/` | HTTP-маршруты, коды ответов, пагинация, фильтры |
| Схемы | `app/schemas/` | Pydantic-модели запросов и ответов, валидация |
| Сервисы | `app/services/` | Бизнес-логика: скоринг тем, анализ конкурентов, Publisher |
| Провайдеры ИИ | `app/ai/` | Единый интерфейс `AIProvider` и реализации |
| Модели | `app/models/` | Таблицы SQLAlchemy |
| Ядро | `app/core/` | Конфигурация, безопасность, шифрование, ошибки, лимиты |
| Задачи | `app/workers/` | Celery-задачи и расписание |

Правило: маршрут не работает с БД напрямую сложной логикой — он вызывает сервис.
Сервис не знает про HTTP. Это позволяет использовать одну и ту же логику
из API и из фоновой задачи.

## 4. Модуль AIProvider

Единая точка подключения любых моделей.

```python
class AIProvider(Protocol):
    name: str
    async def complete(self, request: AIRequest) -> AIResponse: ...
    async def stream(self, request: AIRequest) -> AsyncIterator[str]: ...
```

* `AnthropicProvider` — основная модель (Claude).
* `OpenAIProvider`, `GeminiProvider`, `LocalProvider` — подключаются позже без правки
  вызывающего кода.
* Выбор провайдера — через таблицу `ai_provider_settings` в разрезе проекта.
* Фабрика `get_provider(project_id)` читает настройки, расшифровывает ключ и отдаёт объект.
* Каждый вызов пишет в `ai_usage`: модель, токены, стоимость, промт, задачу.

## 5. Безопасность

* Пароли — bcrypt (с предварительным SHA-256, чтобы снять ограничение в 72 байта).
* Сессия — JWT в httpOnly-cookie (`dp_access` 30 минут, `dp_refresh` 30 дней), SameSite=Lax.
  Токен недоступен из JavaScript, поэтому XSS не даёт угнать сессию.
* API-ключи интеграций — шифрование Fernet (`APP_ENCRYPTION_KEY`), в ответах API
  отдаётся только маска вида `sk-ant-...`.
* SQL-инъекции невозможны: только параметризованные запросы SQLAlchemy.
* Ограничение частоты запросов — Redis, скользящее окно, отдельные лимиты для
  авторизации и для ИИ-операций.
* Защита от повторной отправки — заголовок `Idempotency-Key` на изменяющих запросах.
* Все значимые действия пишутся в `audit_logs`.
* Публикация никогда не выполняется без явного подтверждения пользователя.

Сервис не обходит капчу, не использует чужие cookies и не публикует через чужие аккаунты.
Данные конкурентов берутся из публичных источников, ручного импорта CSV и официальных API.

## 6. Многопользовательская модель

```
User ──< WorkspaceMember >── Workspace ──< Project ──< (конкуренты, темы, статьи, …)
```

В MVP при регистрации автоматически создаётся личное рабочее пространство и первый
проект, поэтому новичок не видит лишних сущностей. Архитектура при этом уже готова
к командам: роли `owner`, `editor`, `author`, `viewer` хранятся в `workspace_members`,
проверка прав вынесена в зависимость `require_project_role(...)`.

## 7. Фоновые задачи

Очередь — Celery на Redis. Каждая задача создаёт запись в `job_runs` со статусом,
прогрессом, временем запуска и завершения, результатом, текстом ошибки и числом попыток.
Пользователь видит прогресс в интерфейсе, а не «зависшую» кнопку.

Задачи: анализ конкурента, обновление публикаций, генерация статьи, пересчёт рейтинга тем,
плановая публикация, повтор неудачных операций, обновление аналитики, уведомления.

## 8. Обработка недоступных данных

Если показатель нельзя получить законным способом, он не выдумывается. В базе хранится
`NULL`, а интерфейс показывает «Данные недоступны» или «Требуется ручной импорт».
Источник каждого значения фиксируется в поле `source` (`manual`, `csv_import`,
`public_page`, `official_api`, `ai_estimate`).
